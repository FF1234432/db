REX data gouvernance a grande echelle : 1000 flux chez un opérateur aéroportuaire international

Gouverner plus de 1000 flux de donnees dans une organisation internationale, c est un defi concret. Ce REX un opérateur aéroportuaire international montre les incidents reels et les solutions mises en place — exactement ce qu on evalue en entretien Data Engineer Senior.

un opérateur aéroportuaire international gere 70 aeroports dans 23 pays. Son la plateforme data ingere quotidiennement des centaines de fichiers envoyes par des equipes metier reparties dans le monde. A cette echelle, la gouvernance n est pas optionnelle.

1Contexte : 622 flux ouverts, 1714 fichiers par jour

  • Stack technique — Cloud SQL (Collector), Airflow (orchestration), BigQuery (stockage), Looker (reporting), portail web (Data Quality Management)
  • Volume — 622 flux ouverts, jusqu a 1714 fichiers recus un lundi, des dizaines d assets (aeroports) contributeurs
  • Problematique centrale — les donnees ne sont pas traitees par une equipe data centrale mais deposees par des utilisateurs metier (Data Owners) dans des dizaines de pays

2Les 3 profils et leurs responsabilites

35 cas concrets d incidents de gouvernance

Question discriminante

Quels sont les types d incidents de qualite les plus frequents dans un pipeline d ingestion de fichiers ? Comment les detectez-vous ?

  • Cas #1 : Absence de fichiers — 8/18 assets n ont pas soumis leurs donnees mensuelles. Le PMO passe des heures en relances email manuelles. Solution : alerting automatique sur l absence de depot dans la fenetre attendue
  • Cas #2 : Fichier non reconnu — un aeroport depose un fichier avec un nom ou format different de celui enregistre. Solution : validation du nom de fichier avant ingestion, retour d erreur automatique au Data Owner
  • Cas #3 : Donnees non actualisees depuis 2 mois — une source automatisee via SFTP a change son format silencieusement. Solution : surveillance continue de la fraicheur des donnees, alerte sur absence de mise a jour
  • Cas #4 : Doublons d ingestion — un aeroport a re-depose un fichier deja traite. Solution : deduplication par hash du fichier + controle de la periode couverte
  • Cas #5 : Donnees erronees exposees — un fichier avec des erreurs a passe le QC et est arrive en production. Solution : tests de plausibilite (min/max, distributions) avant exposition

4La solution : tracer, monitorer, alerter

Question discriminante

Comment automatisez-vous la detection des problemes de gouvernance sans intervention humaine ?

  • Traçabilite bout en bout — chaque fichier est traque depuis le depot SFTP jusqu a l exposition BigQuery : logs Cloud Logging, Airflow dag_runs, portail DQM
  • 3 niveaux d alertes — fichier non identifie (alerte DE), echec qualite (alerte DE + notification Data Owner), echec pipeline (alerte DE)
  • Separation des responsabilites — le Data Owner est responsable de la qualite des donnees qu il envoie. Le DE est responsable de la plateforme. Le portail est une vue simplifiee du monitoring DE a destination des Data Owners
  • Principe cle — l alerting n est qu une couche finale : il faut d abord tracer correctement pour avoir quoi alerter

5Architecture technique

Flux d ingestion un opérateur aéroportuaire international : Source -> [sFTP / Portail / Email / API] | Collector (Cloud SQL) - Identification du fichier - Controle qualite (colonnes, format) | Airflow (ingestion + alignement) - Lecture fichier brut - Mapping vers schema cible - Application des regles de gestion | BigQuery (exposition) - Tables de references - Vues analytiques | Looker / Power BI (consommation) + Cloud Logging (tracabilite) + Portail DQM (monitoring Data Owner)
