Test LookML prêt à l'emploi : modéliser une explore (niveau senior)

Ce test cible la vraie compétence Looker, la plus rare : modéliser en LookML, pas utiliser des rapports existants. On donne un schéma de base et on demande de construire une view et une explore. Le corrigé et les critères permettent de juger même sans être expert Looker.

Le but est de vérifier que le candidat sait modéliser : définir des dimensions et des mesures réutilisables, et relier des tables dans une explore. C'est ce qui garantit des définitions cohérentes pour toute l'entreprise.

1Le brief

La consigne

« Modélise une explore permettant d'analyser le CA des commandes par client et par pays. »

On fournit un schéma de base (commandes, clients) et on demande une view LookML avec des dimensions et mesures, puis une explore reliant les deux tables.

-- Schema de base (tables SQL) commandes(id, client_id, montant, date_commande, statut) clients(id, nom, pays)

    2Le corrigé LookML

    La consigne

    Une modélisation de référence — les noms peuvent varier.

    Voici une view et une explore correctes. L'important n'est pas la syntaxe exacte mais la présence de dimensions et de mesures réutilisables, et d'une jointure propre.

    view: commandes { sql_table_name: commandes ;; dimension: id { primary_key: yes type: number sql: ${TABLE}.id ;; } dimension: statut { type: string sql: ${TABLE}.statut ;; } dimension_group: commande { type: time timeframes: [date, month, year] sql: ${TABLE}.date_commande ;; } measure: ca { type: sum sql: ${TABLE}.montant ;; filters: [statut: "payee"] } } explore: commandes { join: clients { type: left_outer relationship: many_to_one sql_on: ${commandes.client_id} = ${clients.id} ;; } }
    • Des dimensions claires (client, pays, statut, date).
    • Une mesure de CA définie une fois (réutilisable partout).
    • Une explore qui joint proprement commandes et clients.

    Signal d'alerte : le vrai marqueur senior : définir la mesure de CA une fois dans la view (avec son filtre de statut), pour que tout le monde s'appuie sur la même définition. Un candidat qui recalcule le CA à chaque rapport n'a pas compris LookML.

    3Ce qu'on évalue

    La consigne

    La modélisation, pas la mémoire de la syntaxe.

    Un profil senior distingue clairement modéliser et utiliser des rapports, et pense « cohérence pour toute l'entreprise ». Voici les critères.

    • Sait définir des mesures réutilisables (pas des calculs jetables).
    • Relie les tables avec la bonne relation (many_to_one).
    • Ne confond pas Looker et Looker Studio.
    • Pense gouvernance : une définition unique du CA pour tous.

    Ready-to-use LookML test: model an explore (senior level)

    This test targets the real, rarest Looker skill: modelling in LookML, not using existing reports. You give a base schema and ask to build a view and an explore. The answer and criteria let you judge even without being a Looker expert.

    Data Builder·July 2025·11 min read·Looker test · LookML · senior level
    Contents
    1. The brief
    2. The LookML answer
    3. What we assess
    4. Level grid

    The goal is to verify the candidate can model: define reusable dimensions and measures, and join tables in an explore. That's what guarantees consistent definitions across the company.

    1The brief

    The task

    ‘Model an explore to analyze order revenue by customer and country.’

    You provide a base schema (orders, customers) and ask for a LookML view with dimensions and measures, then an explore joining the two tables.

    -- Schema de base (tables SQL) commandes(id, client_id, montant, date_commande, statut) clients(id, nom, pays)

      2The LookML answer

      The task

      A reference modelling — names may vary.

      Here's a correct view and explore. What matters isn't exact syntax but the presence of dimensions and reusable measures, and a clean join.

      view: commandes { sql_table_name: commandes ;; dimension: id { primary_key: yes type: number sql: ${TABLE}.id ;; } dimension: statut { type: string sql: ${TABLE}.statut ;; } dimension_group: commande { type: time timeframes: [date, month, year] sql: ${TABLE}.date_commande ;; } measure: ca { type: sum sql: ${TABLE}.montant ;; filters: [statut: "payee"] } } explore: commandes { join: clients { type: left_outer relationship: many_to_one sql_on: ${commandes.client_id} = ${clients.id} ;; } }
      • Clear dimensions (customer, country, status, date).
      • A revenue measure defined once (reusable everywhere).
      • An explore that cleanly joins orders and customers.

      Warning signal : the real senior marker: defining the revenue measure once in the view (with its status filter), so everyone relies on the same definition. A candidate who recomputes revenue in each report hasn't understood LookML.

      3What we assess

      The task

      The modelling, not syntax memory.

      A senior profile clearly distinguishes modelling from using reports, and thinks ‘consistency for the whole company’. Here are the criteria.

      • Can define reusable measures (not throwaway calculations).
      • Joins tables with the right relationship (many_to_one).
      • Doesn't confuse Looker and Looker Studio.
      • Thinks governance: a single revenue definition for all.
