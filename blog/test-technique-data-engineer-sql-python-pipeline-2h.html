Test technique Data Engineer clé en main : SQL + Python + pipeline (take-home 2h)

Ce test couvre les trois piliers du métier de Data Engineer : requêter (SQL), traiter (Python), et concevoir un pipeline fiable. En version take-home (2h) ou live, il donne une image complète du niveau. Corrigés et grille inclus. Rappel : un take-home non supervisé est moins fiable qu'un live — privilégiez le live si possible.

Data Builder·Juillet 2025·12 min de lecture·Test métier complet · Data Engineer · take-home 2h
Sommaire
  1. Partie 1 — SQL (30 min)
  2. Partie 2 — Python (45 min)

Le fil rouge du métier — et de ce test — est la fiabilité. On ne cherche pas seulement du code qui marche, mais du code robuste, testé, et un pipeline pensé pour l'échec. C'est ce qui distingue un vrai Data Engineer.

1Partie 1 — SQL (30 min)

La consigne

Une requête d'agrégation non triviale + une optimisation.

On demande une requête analytique (ex. le dernier achat de chaque client via une fonction fenêtre) puis comment l'optimiser sur gros volume. On évalue la maîtrise du SQL avancé et la conscience de la performance.

-- Dernier achat de chaque client SELECT * FROM ( SELECT o.*, ROW_NUMBER() OVER (PARTITION BY client_id ORDER BY date_commande DESC) AS rn FROM commandes o ) t WHERE rn = 1;
  • Attendu : une fonction fenêtre (ROW_NUMBER) maîtrisée.
  • Attendu : une piste d'optimisation (index, partition) justifiée.

2Partie 2 — Python (45 min)

La consigne

Écrire un traitement robuste et testé.

On fournit une source imparfaite (un CSV ou une API simulée) et on demande un script qui l'ingère, la fiabilise et gère les erreurs. On regarde surtout la robustesse et la présence de tests.

def nettoyer(df): df = df.drop_duplicates() df["montant"] = pd.to_numeric(df["montant"], errors="coerce") return df.dropna(subset=["id", "montant"]) def test_nettoyer(): brut = pd.DataFrame({"id":[1,1,None], "montant":["10","10","x"]}) assert len(nettoyer(brut)) == 1 # doublon retire, ligne invalide retiree
  • Gère les cas d'erreur (valeurs manquantes, échec de lecture).
  • Écrit au moins un test unitaire sur la logique clé.
  • Code lisible, fonctions réutilisables.

3Partie 3 — Concevoir un pipeline

La consigne

Décrire l'orchestration d'un pipeline quotidien fiable.

Sans forcément coder, le candidat décrit comment il orchestrerait le tout en production : ordre des tâches, relances, alertes, idempotence. C'est la partie la plus discriminante.

  • Ordonne les étapes (extract → transform → load).
  • Prévoit relances, alertes et reprise sans doublons (idempotence).
  • Pense monitoring : comment saura-t-il qu'un run a échoué ?

Signal d'alerte : ce que révèle ce test complet : le SQL et le Python peuvent être bons, mais c'est la partie 3 (fiabilité du pipeline) qui distingue un vrai Data Engineer d'un bon développeur. Un candidat qui néglige la gestion d'échec n'a pas le réflexe du métier.

Turnkey Data Engineer technical test: SQL + Python + pipeline (take-home 2h)

This test covers the three pillars of the Data Engineer role: querying (SQL), processing (Python), and designing a reliable pipeline. As a take-home (2h) or live, it gives a complete picture of the level. Answers and grid included. Reminder: an unsupervised take-home is less reliable than a live one — prefer live if possible.

Data Builder·July 2025·12 min read·Complete role test · Data Engineer · take-home 2h
Contents
  1. Part 1 — SQL (30 min)
  2. Part 2 — Python (45 min)
  3. Part 3 — Design a pipeline
  4. Level grid

The through-line of the role — and this test — is reliability. We don't just want code that works, but robust, tested code, and a pipeline built for failure. That's what marks a real Data Engineer.

1Part 1 — SQL (30 min)

The task

A non-trivial aggregation query + an optimization.

You ask for an analytical query (e.g. each customer's latest purchase via a window function) then how to optimize it at scale. We assess advanced SQL mastery and performance awareness.

-- Dernier achat de chaque client SELECT * FROM ( SELECT o.*, ROW_NUMBER() OVER (PARTITION BY client_id ORDER BY date_commande DESC) AS rn FROM commandes o ) t WHERE rn = 1;
  • Expected: a mastered window function (ROW_NUMBER).
  • Expected: a justified optimization lead (index, partition).

2Part 2 — Python (45 min)

The task

Write a robust, tested processing script.

You provide an imperfect source (a CSV or a simulated API) and ask for a script that ingests it, hardens it and handles errors. We mainly watch robustness and the presence of tests.

def nettoyer(df): df = df.drop_duplicates() df["montant"] = pd.to_numeric(df["montant"], errors="coerce") return df.dropna(subset=["id", "montant"]) def test_nettoyer(): brut = pd.DataFrame({"id":[1,1,None], "montant":["10","10","x"]}) assert len(nettoyer(brut)) == 1 # doublon retire, ligne invalide retiree
  • Handles error cases (missing values, read failure).
  • Writes at least one unit test on the key logic.
  • Readable code, reusable functions.

3Part 3 — Design a pipeline

The task

Describe the orchestration of a reliable daily pipeline.

Without necessarily coding, the candidate describes how they'd orchestrate it all in production: task order, retries, alerts, idempotence. It's the most discriminating part.

  • Orders the steps (extract → transform → load).
  • Plans retries, alerts and duplicate-free recovery (idempotence).
  • Thinks monitoring: how will they know a run failed?

Warning signal : what this complete test reveals: SQL and Python can be good, but it's part 3 (pipeline reliability) that separates a real Data Engineer from a good developer. A candidate who neglects failure handling lacks the role's reflex.
