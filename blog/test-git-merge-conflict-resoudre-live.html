Test Git en entretien : un scénario de merge conflict à résoudre en live

Git est attendu de presque tous les profils data, mais rarement testé. Ce scénario de conflit de fusion, à résoudre en direct, révèle en cinq minutes si un candidat sait vraiment collaborer ou s'il panique au premier obstacle. Corrigé inclus.

Ce qu'on évalue n'est pas la connaissance de commandes exotiques, mais le calme et la méthode : comprendre ce qu'est un conflit, garder l'intention des deux versions, et résoudre proprement.

1Le scénario

La consigne

« Deux collègues ont modifié la même requête SQL. Au merge, voici le conflit. Résous-le. »

Présentez au candidat un fichier avec les marqueurs de conflit Git. Les deux versions ont chacune une intention légitime : il faut les combiner, pas en effacer une au hasard.

<<<<<<< HEAD (ta branche) SELECT id, nom, pays FROM clients WHERE actif = true ======= SELECT id, nom, email FROM clients WHERE pays = 'France' >>>>>>> branche-collegue

    2La résolution attendue

    La consigne

    Comprendre les deux intentions, puis combiner proprement.

    Un bon candidat lit les deux versions, comprend que l'une ajoute des colonnes et l'autre un filtre, puis produit une version qui respecte les deux intentions — après avoir vérifié avec les auteurs si besoin.

    -- Version resolue (les deux intentions combinees) SELECT id, nom, pays, email FROM clients WHERE actif = true AND pays = 'France' # puis : git add requete.sql git commit # finalise le merge
    • Lit et comprend l'intention de chaque version.
    • Combine plutôt que d'écraser une version au hasard.
    • Retire les marqueurs, teste, puis commit proprement.

    Signal d'alerte : le vrai signal n'est pas technique : un bon candidat reste calme, comprend les deux intentions et, en cas de doute, dit « je vérifierais avec les deux auteurs ». Celui qui panique ou écrase une version au hasard révèle un manque d'expérience de collaboration.

    Git interview test: a merge-conflict scenario to resolve live

    Git is expected of almost all data profiles, but rarely tested. This merge-conflict scenario, to resolve live, reveals in five minutes whether a candidate really knows how to collaborate or panics at the first obstacle. Answer included.

    Data Builder·July 2025·9 min read·Git test · collaboration · live
    Contents
    1. The scenario
    2. The expected resolution
    3. Level grid

    What we assess isn't knowledge of exotic commands, but calm and method: understanding what a conflict is, keeping both versions' intent, and resolving cleanly.

    1The scenario

    The task

    ‘Two colleagues changed the same SQL query. On merge, here's the conflict. Resolve it.’

    Show the candidate a file with Git conflict markers. Both versions have a legitimate intent: you must combine them, not erase one at random.

    <<<<<<< HEAD (ta branche) SELECT id, nom, pays FROM clients WHERE actif = true ======= SELECT id, nom, email FROM clients WHERE pays = 'France' >>>>>>> branche-collegue

      2The expected resolution

      The task

      Understand both intents, then combine cleanly.

      A good candidate reads both versions, understands one adds columns and the other a filter, then produces a version honouring both intents — after checking with the authors if needed.

      -- Version resolue (les deux intentions combinees) SELECT id, nom, pays, email FROM clients WHERE actif = true AND pays = 'France' # puis : git add requete.sql git commit # finalise le merge
      • Reads and understands each version's intent.
      • Combines rather than overwriting one version at random.
      • Removes the markers, tests, then commits cleanly.

      Warning signal : the real signal isn't technical: a good candidate stays calm, understands both intents and, if unsure, says ‘I'd check with both authors’. One who panics or overwrites a version at random reveals a lack of collaboration experience.
